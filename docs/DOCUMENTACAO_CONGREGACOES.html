Documentação interativa · Multi-tenant

Como as congregações veem, administram e se isolam no sistema

Este guia explica — com exemplos e simulação — o modelo de isolamento de dados do IADMPMA: o que cada congregação enxerga ao entrar no painel /admin, como o sistema impede uma igreja de ver os dados da outra, e onde a fronteira realmente está.

Next.js App Router NextAuth v5 + JWT Prisma + PostgreSQL (Neon) RBAC granular 278 testes passando

1Visão geral do modelo

O sistema é multi-tenant: uma única instância atende várias igrejas, mas cada igreja só enxerga os próprios dados. A fronteira dura de isolamento é a Organização.

🏢

Organização = tenant

Cada igreja (matriz, filial autônoma ou rede) é uma Organizacao. Todo registro de negócio carrega organizacaoId. É o que separa de verdade os dados.

⛪

Congregação = sub-unidade

Dentro de uma organização existem várias Congregacao (ex.: Cohabiano, Vila Sarney). Ela classifica registros (congregacaoId), mas não é um tenant isolado.

👤

Usuário com vínculo

O acesso nasce do vínculo UsuarioOrganizacao (usuário ↔ organização). Sem vínculo, não há dados para ver — mesmo que a role seja alta.

Resposta direta: as congregações veem o painel normalmente, mas cada uma só opera dentro da sua Organização. Tentar acessar outra organização resulta em 403 (“Sem permissão para esta organização”) e gera registro de auditoria ACESSO_NEGADO. Já as congregações internas de uma mesma organização dividem o mesmo acesso — entre elas a separação é por filtro/relatório, não por bloqueio (ver seção 11).

2Organização × Congregação

São dois níveis diferentes. Confundir os dois é o erro mais comum ao configurar o sistema.

🏢 Organização — o isolamento real

Ex.: “IADMP Central”, “IADMP Filial Norte”. Possui slug próprio, site público próprio, configurações próprias e usuários vinculados. Ninguém de fora entra.

⛪ Congregação CohabianoMembros, liturgias, eventos…
⛪ Congregação Vila SarneyMembros, liturgias, eventos…
⛪ Congregação Novo RenascerMembros, liturgias, eventos…

Registros de negócio

Todos com organizacaoId (obrigatório, com índice) + congregacaoId (opcional): Membro, Liturgia, Evento, Aviso, Lideranca, EventoFinanceiro, Galeria, Oportunidade, Agenda, Inscricao…

O design atual é intencional

  • O sistema foi desenhado para multi-igreja, não para multi-sede isolada: a fronteira de segurança é a organização.
  • Dentro de uma igreja, o pastor/admin precisa enxergar todas as congregações (relatórios consolidados, financeiro, comparativos).
  • A congregação é usada como dimensão de filtro: em /api/membros?congregacaoId=…, relatórios e no painel de indicadores.
  • Se no futuro for preciso que um líder de congregação só veja a própria congregação, o ponto de extensão já existe: campo congregacaoId + helpers de escopo em src/lib/tenant.ts.

Resolução por nome (find-or-create)

O formulário pede o campo texto “Congregação”. Ao salvar, resolveCongregacaoId() executa:

// src/lib/tenant.ts — resolveCongregacaoId()
1. Se veio congregacaoId  → valida se pertence à organização (senão ORG_FORBIDDEN)
2. Se veio só o nome         → procura Congregacao na organização
3. Se não existir             → cria a congregação dentro da organização
4. Se não veio nada           → null (registro sem congregação)

Isso significa que digitar “Matriz” pela primeira vez cria a congregação automaticamente — sem passo extra de cadastro.

3As 4 camadas do isolamento

O isolamento não depende de uma única barreira. São quatro, empilhadas. Clique em cada uma para ver o código.

1

Banco de dados — coluna obrigatória

Prisma›

Toda entidade de domínio tem organizacaoId com FK e índice. Um registro simplesmente não existe sem uma organização dona.

model Membro {
  organizacaoId  String           // obrigatório, com índice
  congregacaoId  String?          // opcional — sub-unidade
  organizacao    Organizacao      @relation(...)
  congregacao    Congregacao?     @relation(...)
}

Consulta de um usuário com escopo SINGLE (1 org):

prisma.membro.findMany({ where: { organizacaoId: { in: ['org_A'] } } })
2

API — escopo resolvido no servidor

tenant.ts›

As rotas de negócio chamam resolveOrgScope() (ou canManageOrganization()) antes de consultar o banco. Hoje 44 das 69 rotas importam src/lib/tenant.ts; as demais usam os helpers equivalentes de auth-helpers. O cliente nunca decide o escopo.

// GET /api/membros (src/app/api/membros/route.ts)
const user   = await requireAuth();
const scope  = await resolveOrgScope(user, organizacaoId);
if (scope.mode !== 'ALL') where.organizacaoId = { in: scope.orgIds };

Funções centrais de src/lib/tenant.ts:

  • resolveOrgScope(user, orgId) → modos ALL (SUPER_ADMIN), SINGLE e MULTI
  • resolveTargetOrgId() → decide a organização de uma escrita (POST/PATCH)
  • assertOrgAccess() → confirma vínculo e audita ACESSO_NEGADO quando nega
  • withOrgScope() / orgFilter() → injetam o filtro no where do Prisma
3

RBAC — sessão, role e permissões

NextAuth v5›

Autenticação por cookie JWT (authjs.session-token). O middleware protege /admin/* e as rotas chamam:

requireAuth()                      // 401 sem sessão
requireSuperAdmin()                // 403 se não for SUPER_ADMIN
hasPermission(id, 'membros', 'criar') // 403 se o perfil não permite
canAssignRole(requester, role)     // impede subir de nível sozinho

Hierarquia: SUPER_ADMIN(100) > ADMIN(90) > PASTOR(85) > ADMIN_IGREJA(80) > LIDER/LIDER_MINISTERIO(60) > SECRETARIA/FINANCEIRO/EDITOR_SITE(50) > COORDENADOR(40) > MUSICO(20) > MEMBER(10)

4

Site público — separado por slug

/igreja/[slug]›

As APIs públicas não usam sessão: resolvem a organização via resolvePublicOrganizacaoId() — prioridade slug > organizacaoId > fallback (primeira organização ativa, ordenada por criação). Se o slug não existir ou a org estiver inativa, não fica vazio: o sistema cai na primeira org ativa (cuidado ao interpretar páginas vazias).

GET /api/public/eventos?slug=iadmp-central
// resolveOrgBySlug(slug) → organizacaoId → where.organizacaoId = id

Rota pública da igreja: /igreja/iadmp-central/eventos, /lideranca, /galeria, /contato…

4Fluxo de uma requisição

O que acontece quando um líder clica em “Membros” no painel.

Login em /admin/login

NextAuth valida credenciais (bcrypt) e cria o cookie authjs.session-token com id, role e organizacoes[]. Usuário inativo (ativo: false) é bloqueado.

Middleware valida o cookie

src/middleware.ts protege /admin/:path*: sem cookie, redireciona para o login. A página carrega, mas os dados ainda não.

Seletor de organização no sidebar

O layout busca GET /api/organizacoes, que devolve só as organizações do usuário (SUPER_ADMIN recebe todas as ativas). A escolha fica salva em localStorage: iadmp-current-org e ao trocar a página recarrega.

Atenção: por padrão as listagens não enviam esse valor ao servidor — elas usam o escopo completo dos vínculos (união das orgs). Só formulários/abas que pedem ?organizacaoId explicitamente são afetados (ver seções 7 e 11).

Fetch da lista — escopo aplicado no servidor

fetch("/api/membros") (sem organizacaoId na maioria das telas) → requireAuth() → resolveOrgScope() → where.organizacaoId = { in: orgIds }. Usuário de 1 org vê só a dela; usuário MULTI vê a união das vinculadas. O registro de outra igreja nunca sai do banco.

Escrita validada e auditada

POST/PATCH passa por Zod (src/lib/validations.ts), resolveTargetOrgId(), resolveCongregacaoId() e grava AuditLog com ação CREATE/UPDATE/DELETE. Tentativa fora do escopo → 403 + ACESSO_NEGADO.

      7Passo a passo: como uma congregação administra
      
  
      Rotina do dia a dia de quem entra no painel para cuidar da própria congregação.
      

  
      
    
      
      
      Entrar com o usuário da congregação
      
      
      Acesso direto em /admin/login. O administrador da igreja cria o usuário em /admin/usuarios e marca a organização dele (multi-seleção possível).
      
    
      
    
      
      
      Conferir a organização ativa no topo do menu
      
      
      Se tiver 1 org, fica fixa. Se tiver várias, o seletor aparece no topo do sidebar; trocar salva em localStorage e recarrega a página. Hoje o seletor não refiltra as listagens — elas mostram a união das orgs vinculadas; o valor é usado nas telas/abas que enviam ?organizacaoId (ex.: Centro de Gestão, modelos de liturgia, site público).
      
    
      
    
      
      
      Cadastrar preenchendo “Congregação”
      
      
      Em Membros, Liturgia, Eventos, Avisos, Liderança, Financeiro e Galeria existe o campo Congregação. Basta digitar o nome (ex.: “Vila Sarney”) — ele vira congregacaoId automaticamente dentro da organização.
      
    
      
    
      
      
      Filtrar para ver só a sua congregação
      
      
      As APIs aceitam ?congregacaoId=… (membros, eventos, avisos, liderança, financeiro e indicadores), mas as listagens do painel ainda não expõem um seletor de congregação — hoje a filtragem por congregação aparece nos relatórios (/admin/relatorios exporta CSV com a coluna Congregação) e no Centro de Gestão.
      
    
      
    
      
      
      Nada vaza — e tudo é registrado
      
      
      Criações/edições geram AuditLog. Tentativas fora do escopo geram ACESSO_NEGADO com o motivo em /admin/gestao?aba=auditoria (aba Auditoria do Centro de Gestão).

      11Limites atuais (importante)
      
  
      Transparência sobre o que o isolamento cobre hoje — e o que ele não cobre.
      
  
      
    
      
      
      ✔ Isolado de verdade
      
      
        
        
      • Dados entre organizações (igrejas distintas)
        • 
        
      • Escritas: criação/editição em org alheia
        • 
        
      • Gerência de organizações, usuários e permissões
        • 
        
      • Sites públicos (cada slug vê só a sua org)
        • 
        
      • Auditoria de tentativas negadas
        • 
      
      
    
      
    
      
      
      ⚠ Não é bloqueado hoje
      
      
        
        
      • Congregações dentro da mesma organização: um usuário com acesso à org vê as congregações dela — a separação é por filtro (congregacaoId), não por perfil
        • 
        
      • Não existe vínculo “usuário ↔ congregação” no schema (UsuarioOrganizacao só tem organizacaoId + perfilId)
        • 
        
      • Campo de congregação é texto livre com find-or-create (variações de nome criam congregações duplicadas se não houver padrão)
        • 
      
      
    
      
  
      
  
      
    Se for necessário isolamento por congregação: o caminho já está mapeado — adicionar
    congregacaoId opcional em UsuarioOrganizacao, estender resolveOrgScope() para
    devolver também o escopo de congregação e aplicá-lo em withOrgScope(). 44 das 69 rotas de API já importam
    src/lib/tenant.ts (as demais usam canManageOrganization() de auth-helpers), então a mudança seria centralizada.
  
      

      



      
  
      12Perguntas frequentes
      
  
      Clique para abrir.
      

  
      
    Uma congregação consegue ver os dados da outra?
    
      Depende do nível. Entre organizações diferentes (igrejas distintas): nunca — o banco filtra e a API retorna 403. Entre congregações da mesma organização: sim, quem tem acesso à organização enxerga todas as congregações dela; existe filtro ?congregacaoId= nas APIs e nos relatórios para concentrar a visão na própria (as listagens do painel ainda não exibem seletor de congregação).
      
  
      
  
      
    Como o sistema sabe em qual organização o usuário está?
    
      Pela tabela UsuarioOrganizacao (vínculo usuário ↔ organização), lida no servidor via resolveOrgScope(). O seletor do sidebar salva a preferência em localStorage ('iadmp-current-org') e recarrega a página, mas ele não muda sozinho o filtro das listagens — essas usam o escopo completo dos vínculos. Em nenhum caso o seletor amplia o escopo além do vínculo.
      
  
      
  
      
    O que impede eu passar ?organizacaoId=deoutrapessoa na URL?
    
      resolveOrgScope() compara o organizacaoId pedido com a lista de vínculos do usuário. Se não estiver na lista, lança ORG_FORBIDDEN → 403 “Sem permissão para esta organização” e registra ACESSO_NEGADO na auditoria.
      
  
      
  
      
    Criar membro exige cadastrar a congregação antes?
    
      Não. Basta digitar o nome no campo “Congregação”: resolveCongregacaoId() procura dentro da organização e cria se não existir. Também é possível enviar congregacaoId diretamente — nesse caso o sistema valida se ela pertence à organização.
      
  
      
  
      
     SUPER_ADMIN vê tudo sem vínculo nenhum?
    
      Sim. A role SUPER_ADMIN opera em modo ALL: não tem filtro de organização, enxerga todas as organizações ativas no seletor e pode criar/gerenciar organizações em /admin/organizacoes. Ele também recebe todas as permissões (getUserPermissions() devolve o catálogo completo).
      
  
      
  
      
    Um usuário pode se promovendo a SUPER_ADMIN?
    
      Não. canAssignRole() compara a hierarquia e só permite atribuir roles de nível inferior ao do solicitante. Alterações de role/permissão passam sempre pela sessão, nunca pelo body enviado pelo cliente.
      
  
      
  
      
    O que acontece com o site público se a organização for desativada?
    
      resolveOrgBySlug() só retorna organizações com ativo: true, porém resolvePublicOrganizacaoId() tem fallback: slug desconhecido ou org inativa faz o sistema usar a primeira organização ativa (ordenada por criação). Ou seja: o site não fica vazio — ele pode exibir o conteúdo da organização padrão. Se quiser bloqueio total, esse fallback é o ponto a ajustar.
